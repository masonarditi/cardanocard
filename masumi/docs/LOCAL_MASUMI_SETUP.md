# Local Masumi setup — next milestone

The application remains in local simulation mode. This setup adds a local Masumi Payment Service and PostgreSQL; Cardano transactions still require access to the external Preprod test network.

## Current prerequisites

- Docker Desktop installed; daemon must be running.
- Private local node credentials: generated by `scripts/prepare_masumi.py`.
- Blockfrost **Cardano Preprod** project key: obtain at [Blockfrost](https://blockfrost.io/) and save as `BLOCKFROST_API_KEY_PREPROD` in `infra/masumi/.env`.
- No Mainnet key, real funds, or AgentCard access is needed for this milestone.

## Start sequence

Run from the repository root:

```sh
.venv/bin/python scripts/prepare_masumi.py
# Add the Blockfrost Preprod project key to infra/masumi/.env, then:
docker compose --env-file infra/masumi/.env -f infra/masumi/compose.yaml config --quiet
docker compose --env-file infra/masumi/.env -f infra/masumi/compose.yaml up -d
.venv/bin/python scripts/check_masumi.py
```

The preparation script refuses to overwrite an existing `.env`. Do not rotate the encryption key after wallet data exists without the provider's migration procedure. Keep the `.env` and Docker database volume together when backing up the node.

Admin UI: `http://127.0.0.1:3001/admin`. API docs: `http://127.0.0.1:3001/docs`. The admin credential is the private `ADMIN_KEY` in `infra/masumi/.env`; do not paste it in chat or logs.

Only port 3001 is exposed, on localhost. PostgreSQL has no published host port. The stack uses its own Compose project and persistent volume. No shared Docker resources are removed.

The Payment Service image version `0.22.0` is taken from the official quickstart. It is a candidate baseline, not a claim that the Python SDK or x402 V2 has passed compatibility testing. Inspect the running OpenAPI before wiring the application. The node runs migrations and seeds only an empty database. With empty mnemonic fields, upstream seeding generates purchasing and selling test wallets; export/back them up privately. With an empty collection address, this local test setup uses the selling wallet as the collection destination.

## After the node is healthy

1. Verify Preprod configuration, API authentication, contract/payment types, required fields, timestamp units, and hash composition against the running service.
2. Inspect the generated purchasing and selling addresses, configure the collection destination, and back up wallet access securely.
3. Fund both wallets with faucet test ADA; verify confirmed balances. Fee-token choice follows the actual service/registry support.
4. Establish registration prerequisites. A local node can reach our API via `host.docker.internal:8080` only if the agent accepts that route; the current server deliberately binds to loopback. Public registry discovery requires an appropriate reachable endpoint and will be a separately scoped exposure step.
5. Create the registered agent identity and fixed test service price; copy agent ID and seller vkey into the application's private `.env` only after validation. Keep seller and buyer permissions distinct.
6. Finish the real buyer adapter and verify one test escrow → fake purchase success → result → payout.
7. Verify one test escrow → fake decline → buyer refund request → seller authorization → refund withdrawal.
8. Capture testnet transaction identifiers and independently verify result hashes. Label the merchant purchase as simulated.

Do not mark `MASUMI_V1_COMPATIBLE=true` or enable the live adapter just because `/health` succeeds. Passing node health is distinct from contract/API compatibility and real escrow proof.

## Stop without deleting wallet data

```sh
docker compose --env-file infra/masumi/.env -f infra/masumi/compose.yaml stop
```

Do not use `down -v` to troubleshoot: that deletes the persistent database volume.
